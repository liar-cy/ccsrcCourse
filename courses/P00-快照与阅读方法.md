# P00 Claude Code 源码快照与阅读方法

> 这门课先解决“我们手里的到底是不是完整源码、哪些结论可以相信、应该从哪里开始读”。

## 学习目标

学完本课，你应该能够：

- 说清 npm 发布包、`cli.js`、`cli.js.map` 和 `restored-src/` 的关系；
- 区分 Claude Code 自有源码、第三方依赖和原生 vendor 代码；
- 使用 source map 中的 `sources` 与 `sourcesContent` 验证一个源码文件；
- 理解“能在 source map 中看到”和“公共构建实际启用”不是一回事；
- 为后续课程建立可重复的源码取证方法。

## 前置知识与范围

本课不要求 TypeScript 基础，也不讲 Agent 循环。我们只研究当前仓库中的 **2.1.88 客户端快照**。

本课不包含：Anthropic 服务端、模型权重、官方内部 monorepo、完整构建系统和提交历史，因为这些内容不在发布包 source map 中。

阅读约定：标为“教学简化版”或包含“略”的代码块会删去与当前问题无关的类型、日志或分支；其余短摘录均可在所列源码锚点核对。

## 先用 Python 建立最小模型

Source map 在这里可以先理解成两个等长数组：

- `sources[i]`：第 `i` 个原始文件的路径；
- `sourcesContent[i]`：这个文件的正文。

下面是教学简化版提取器，只提取 Claude Code 自有的 `../src/`：

```python
import json
from pathlib import Path

source_map = json.loads(Path("package/cli.js.map").read_text())
output = Path("restored-src/src")

for source_path, content in zip(
    source_map["sources"], source_map["sourcesContent"]
):
    if not source_path.startswith("../src/"):
        continue
    relative = source_path.removeprefix("../src/")
    target = output / relative
    target.parent.mkdir(parents=True, exist_ok=True)
    target.write_text(content)
```

它保留了真正重要的映射关系：路径和正文按数组下标配对。仓库脚本还要处理 webpack 前缀、查询参数、`..` 和第三方依赖路径。

## Claude Code 快照的真实结构

### 1. 发布元数据确认版本

源码锚点：[package.json](../claude-code-sourcemap/package/package.json)

```json
{
  "name": "@anthropic-ai/claude-code",
  "version": "2.1.88",
  "bin": { "claude": "cli.js" },
  "engines": { "node": ">=18.0.0" },
  "type": "module"
}
```

解读：

- npm 包名和版本明确指向 Claude Code 2.1.88；
- `claude` 命令实际启动 `cli.js`；
- 这是 JavaScript/TypeScript 客户端，不是 Rust crate；
- `cli.js` 是打包结果，适合运行和交叉验证，不适合从头阅读。

执行 `node package/cli.js --version` 会得到 `2.1.88 (Claude Code)`，因此版本结论属于证据等级 A。

### 2. 仓库提取脚本做了什么

源码锚点：[extract-sources.js](../claude-code-sourcemap/extract-sources.js)

```javascript
const rawMap = JSON.parse(fs.readFileSync(mapFile, 'utf8'));

for (let i = 0; i < rawMap.sources.length; i++) {
  const sourcePath = rawMap.sources[i];
  const content = rawMap.sourcesContent && rawMap.sourcesContent[i];
  if (!content) { skipped++; continue; }
  // 清洗路径，创建目录，然后写入 content
}
```

解读：

1. 脚本没有“反编译” `cli.js`；它直接读取 source map 附带的原始正文。
2. `sourcesContent` 已经包含可读的 TS/TSX，因此还原质量远好于美化压缩后的 bundle。
3. 写入前必须清洗路径，避免绝对路径和 `../` 逃出目标目录。
4. 当前脚本首行引入了 `SourceMapConsumer`，但后续没有使用它。缺少 `source-map` 包时脚本会在真正解析 JSON 前失败；本仓库的已提取结果使用相同清洗逻辑直接解析 JSON 得到。

### 3. 为什么日志显示 4,756，磁盘只有 4,471 个文件

当前快照实测：

| 指标 | 数量 | 含义 |
|---|---:|---|
| source map 来源条目 | 4,756 | `sources.length` |
| 落盘唯一文件 | 4,471 | 规范化路径相同的条目会覆盖同名文件 |
| `restored-src/src/` 自有文件 | 1,902 | Claude Code 主课程范围 |
| 自有 TS/TSX 文件 | 1,884 | 绝大多数自有实现 |
| `restored-src/node_modules/` 唯一文件 | 2,565 | 第三方依赖，默认排除 |
| `restored-src/vendor/` 文件 | 4 | 随包进入的 vendor 源码 |

“写入 4,756 次”不等于“生成 4,756 个不同路径”。这个差异主要来自规范化后重复的第三方路径，不能据此判断源码丢失；自有 `src/` 的 1,902 个路径是唯一的。

## 如何区分自有源码与依赖

判断规则应基于 source map 的原始路径，而不是看到文件内容后猜作者：

```text
../src/...          → Claude Code 自有客户端源码
../node_modules/... → 第三方依赖
../vendor/...       → vendor 源码
```

例如：

- [`src/query.ts`](../claude-code-sourcemap/restored-src/src/query.ts) 是 Agent 循环主文件；
- [`src/screens/REPL.tsx`](../claude-code-sourcemap/restored-src/src/screens/REPL.tsx) 是交互界面主文件；
- `restored-src/node_modules/lodash-es/` 是第三方工具库，不应算入 Claude Code 自有架构。

`utils/` 虽然有 500 多个文件，但它也不是一个独立架构层。后续课程会按消息、权限、模型、插件等业务职责重新归类。

## 三类“缺失”必须分开

### source map 没有某个被 import 的文件

还原源码有时会 import 一个 `.js` 模块，但 source map 没有为它提供独立的源文件。这可能来自打包内联、生成代码、宏替换或快照不完整。不能自行创建一个同名文件来补全事实。

### source map 有源码，但公共 bundle 裁掉了

入口中大量使用：

```typescript
if (feature('SOME_FEATURE')) {
  const module = await import('../some-feature/main.js')
  await module.run()
}
```

`feature()` 是构建期能力开关。source map 可能保留某条源码路径，而公共 `cli.js` 中该条件已经被替换为 `false` 并做死代码删除。此类结论属于证据等级 B，不能写成“用户现在可以使用”。

### 客户端源码本来就不包含服务端

客户端能看到请求参数、工具 schema、system prompt 组装和流事件处理；看不到模型如何推理，也看不到 Anthropic 服务端的完整调度实现。客户端注释提到服务端文件名，也不等于该服务端源码已经泄露。

## 推荐的源码阅读法

### 第一步：从可运行行为建立问题

例如先确认：

```bash
node claude-code-sourcemap/package/cli.js --version
```

然后提出问题：“为什么 `--version` 启动得很快？”再去读 `src/entrypoints/cli.tsx` 的快路径，而不是先读 4,684 行的 `main.tsx`。

### 第二步：沿调用链追踪

以一条用户请求为例：

```text
entrypoints/cli.tsx
  → main.tsx
  → screens/REPL.tsx 或 QueryEngine.ts
  → query.ts
  → services/api/claude.ts
  → services/tools/*
```

每次只追踪一个正常路径，再补一个错误/取消路径。

### 第三步：记录状态所有者

遇到函数时，不只问“它做什么”，还要问：

- 输入从哪里来？
- 它修改的是局部变量、React store、会话文件还是远端状态？
- 这个状态跨一次 API 请求、一次用户 turn，还是整个 session？
- 谁消费输出？

### 第四步：用 bundle 做交叉验证

对 feature flag、版本和公共行为有疑问时，在 `package/cli.js` 搜索相关字符串。源文件存在但 bundle 中分支恒为 `false`，只能说明设计或内部构建能力，不能说明公共版本已启用。

## 失败路径、安全边界与设计取舍

| 情况 | 正确处理 | 不正确的推断 |
|---|---|---|
| 提取脚本缺依赖 | 说明脚本阻断点，直接验证 JSON 数组或补齐工具依赖 | 宣称 source map 损坏 |
| 同名路径覆盖 | 分别报告来源条目和唯一文件数 | 把每次写入都算成独立文件 |
| import 目标未还原 | 标记快照缺口，沿 bundle 或调用方继续验证 | 虚构缺失实现 |
| feature-gated 源码 | 标注证据等级 B，并检查 bundle | 宣称功能已上线 |
| `node_modules` 源码 | 仅在解释协议边界时引用 | 计入 Claude Code 自研模块 |

提取路径清洗也是安全边界：不能让 source map 中的绝对路径或 `../` 把文件写到 `restored-src/` 外部。

## 源码锚点

| 文件/符号 | 在流程中的职责 | 建议关注 |
|---|---|---|
| `package/package.json` | 发布包身份和入口 | 版本、bin、运行时 |
| `package/cli.js` | 公共可执行 bundle | 行为交叉验证、构建期开关结果 |
| `package/cli.js.map` | 源码正文与映射 | `sources`、`sourcesContent` |
| `extract-sources.js: extractSources` | 批量落盘 | 路径清洗、空正文处理、覆盖行为 |
| `restored-src/src/entrypoints/cli.tsx: main` | 自有源码入口 | 下一课的启动快路径 |

## 小结与检查题

本课最重要的结论：我们拥有的是 **客户端发布快照的高质量 source map 还原物**，不是完整官方仓库。它足以研究 Claude Code 的 Agent harness，但每个结论都必须标注快照和启用边界。

3. 看到一个 feature-gated 文件时，至少还需要检查什么？
4. 为什么模型推理过程不在本快照的研究范围内？
